Phase 1 declarations for [design 25](../../../designs/25-fnox-secret-delivery.md), disconnected from current consumers. This inventory covers all 95 `.secrets.jsonc` entries and the additional tracked text references. No secret value was accessed, no consumer was changed, and no deployment or vault-item deletion occurred.

## Effective sets and accounts

Root `fnox.toml` declares 31 unconditional shared references. Each host file imports root once. Its top-level providers and secrets become the filename's native profile; invoke the explicit host config **and** selected profile together. There are no operation profiles, inactive compatibility profiles, defaults, sync entries, leases, or file-output modes. `env = "exec"`, `if_missing = "error"`, `prompt_auth = false`, and disabled daemon settings come from root.

Their `agent` provider overrides the complete desktop provider, with a token reference and no account flag.

Fnox v1.35.1 accepts `account = { secret = "FNOX_WORK_ACCOUNT" }`. The account environment value is nonsecret metadata, not another remote text credential. The isolated binary test passed `FAKE_WORK_ACCOUNT` through to `op --account` for corporate reads, while personal reads retained the verified UUID. Removing the environment value caused strict exec to fail before the child. **Work setup prerequisite:** obtain the full corporate account UUID or verified unambiguous sign-in address on the work laptop and supply it as `FNOX_WORK_ACCOUNT`. No UUID was invented and no prefix discovery is configured. Do not call work activation complete until its uncommitted sources and both real accounts have been checked.

Physical selection remains `Thurstons-MacBook-Pro → macos`, `ML-DFC6YK6VJQ → work`, and `pod042 → pod042`. Orb is explicit runner selection. Omarchy is not registered. The launcher must isolate global config, pass strict/no-daemon flags, reject unintended config overlays, clear desktop service/Connect authority, and scrub inherited provider authority. These files cannot retract arbitrary credentials already inherited from an old shell. Only the explicitly configured env=false names are scrubbed by native fnox.

### Consumer ownership versus shared exposure

The table below records intended consumer ownership, not a claim that every host currently runs every application. Shared placement is based on at least two supported environments: desktop/NAS chezmoi and agent consumers, or the repository's host-independent edge/UniFi development tasks available on macos and the retained Orb runner. The user confirmed Orb retains repository Cloudflare, UniFi, Worker and controller workflows at parity, without special restrictions. No real Orb deployment was performed. `NEXTDNS_PROFILE_ID` is shared for macos/Orb's native UDMP controller workflow and pod042's retained Homepage consumer; it is not a machine-specific login credential.

Work excludes personal rclone/eightctl/Library outputs but still receives their shared values during exec. Pod042 also receives edge development credentials. This broader union and availability dependency are accepted; private corporate references never enter root. The Library CF Access client is macos-only, with Orb's AIG workflow providing the second owner. An unignored pod042 eightctl/rclone template is a concrete render consumer, not proof those clients are useful on the NAS.

Alerting, backup and Samba references retain the declared pod042 capability intent. They do not activate native resources, restore services, or enable timers. Healthchecks still waits for timer implementation. Full-host eager resolution nevertheless makes those declared credentials availability prerequisites now, before capability activation.
