# Docker runtime on Proxmox VE

> Research only. This bounds the direct-host and single-LXC options for the bunker rebuild; it does not select one. It deliberately does not revisit the Docker-bridge/published-port network decision.

## Scope and evidence standard

The target is one i5-12600K / 96 GiB ZFS NAS running approximately twelve Compose stacks. Plex needs the host Intel QuickSync render device (`/dev/dri`); the stacks need read/write access to host ZFS datasets. The host will be reconciled by Ansible. There is no PVE cluster, and the UniFi gateway—not PVE firewall rules—does network segmentation. One or two ordinary VMs may remain.

**Documented** below means an upstream Docker or Proxmox document, or a Proxmox staff statement. **Report** means a dated, first-hand forum report: useful evidence of an operational edge, but neither a guarantee nor a supported configuration. Community popularity is not evidence that a failure mode is absent.

## The official position

Proxmox makes two distinct recommendations, neither of which endorses the two options under consideration:

- The [PVE FAQ](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#_lxc_vs_lxd_vs_proxmox_containers_vs_docker) says, precisely: **“It is not recommended to run docker directly on your Proxmox VE host.”** It then says application containers directly as Proxmox Containers are a technology preview and, for orchestration or live migration, recommends a Proxmox QEMU VM.
- Proxmox staff member Tom's direct answer to bare-metal / VM / LXC Docker in 2020 was: **“I highly recommend to install Docker inside a VM.”** ([forum post](https://forum.proxmox.com/threads/docker-installation-on-baremetal-vm-lxc.68364/)). The PVE FAQ's VM recommendation is the current product documentation; the staff post establishes that this is not just a community inference.
- There is no official manual sentence saying “Docker in an LXC is unsupported” in those exact words. The current LXC documentation instead explicitly documents the features required by the setup: `keyctl` is “required to use docker inside a container,” and `nesting` permits nesting but exposes host `procfs` and `sysfs` to the guest ([Linux Container](https://pve.proxmox.com/wiki/Linux_Container)). That documents feasibility, not support.
- Fabian Grünbichler, Proxmox staff, put the support rationale more directly in a 2023 thread: “like docker, running podman inside LXC is asking for trouble. please use a proper VM for such workloads.” His explanation: LXC constrains processes while Docker/Podman want to manage those constraints, “an inherent conflict … that requires workarounds that can break at any time.” ([forum post](https://forum.proxmox.com/threads/podman-in-lxc-what-do-overlay-not-support-file-handles-and-conflicting-options-userxattr-metacopy-mean.121825/))

The official position is thus clear about the preferred architecture—Docker in QEMU—but needs careful interpretation here: the usual VM rationale is strong isolation and live migration. QuickSync sharing and direct ZFS dataset access are specifically the reasons a VM has already been rejected for this host.

## Docker directly on the PVE host

This has the least storage and device plumbing. It also makes Docker's privileged daemon, its package repository, cgroups, and packet-filter rules part of the hypervisor's own lifecycle.

### Concrete failure modes

| Risk | What is actually documented or reported | Does it bite here? |
| --- | --- | --- |
| Docker changes host firewall state | **Documented.** Docker creates packet-filter rules in the *host* network namespace for bridge networks. With the iptables backend, if Docker itself enables IP forwarding, it also changes the filter-table `FORWARD` default policy to `DROP`. Docker documents `ip-forward-no-drop: true` to retain the policy, and `DOCKER-USER` rules to explicitly permit forwarding between host interfaces. See [Docker packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/) and [Docker with iptables](https://docs.docker.com/engine/network/firewall-iptables/). Docker can alternatively use its nftables backend, but Docker calls it experimental and says it does not enable forwarding or create a default drop policy. | **Conditional, not eliminated.** This is relevant only to packets that traverse the host's IP forwarding/filter path. Ordinary switching across one Linux bridge need not do that; routed guest networks, bridge netfilter, multiple bridged interfaces, or host-mediated forwarding can. A PVE forum operator reported PVE 7 guests losing networking after Docker's `FORWARD` change ([report](https://forum.proxmox.com/threads/running-docker-on-the-proxmox-host-not-in-vm-ct.147580/)); it is credible, but does not prove every `vmbr0` setup is affected. Before relying on direct host Docker, test the exact bridge/VLAN/VM paths with Docker started and restarted. |
| Conflict with `pve-firewall` | **Documented mechanism; PVE-specific conflict is a report.** PVE's stock firewall manages iptables rules; its newer `proxmox-firewall` manages two dedicated nftables tables ([PVE Firewall](https://pve.proxmox.com/pve-docs/chapter-pve-firewall.html)). Docker owns global iptables chains/default policy or its own nftables tables. The cited PVE operator specifically attributes guest breakage to Docker's interference with PVE firewall rules. | **Mostly avoided, not zero.** The PVE firewall is intentionally unused, so there is no PVE ruleset to preserve. Docker's own global forwarding/NAT policy still affects any guest traffic routed through the host. The UniFi gateway performing LAN/VLAN routing makes that narrower than a PVE-router design. |
| Upgrade package/repository friction | **Documented precondition and one direct report.** Both [PVE 7→8](https://pve.proxmox.com/wiki/Upgrade_from_7_to_8) and [PVE 8→9](https://pve.proxmox.com/wiki/Upgrade_from_8_to_9) tell customized systems with third-party packages/repos to ensure they are upgraded and compatible with the new Debian release. Docker's own Debian instructions use a release-specific apt repository and require deliberate Docker package upgrades ([Docker Debian install](https://docs.docker.com/engine/install/debian/)). A PVE 8.4→9.1 operator's upgrade became broken when Debian's `docker-compose` tried to overwrite the plugin supplied by `docker-compose-plugin 5.0.1-1~debian.12~bookworm`; a Proxmox staff member advised removing one of the conflicting packages ([report and staff response](https://forum.proxmox.com/threads/failed-proxmox-9-upgrade-from-v8-4-16.179282/)). | **Real maintenance work.** The 8→9 report is a package ownership conflict, not evidence that `dockerd` cannot run on PVE 9. A targeted search did not find an equally concrete first-hand PVE 7→8 failure specifically naming `docker-ce`; the correct conclusion is not that 7→8 was frictionless. The official requirement to audit third-party repos applies to both upgrades. Ansible can make the Docker source/pins and a pre-upgrade remove/reinstall plan declarative, but it cannot make cross-release apt ownership conflicts disappear. |
| cgroup conflict | **No direct-host Docker/PVE conflict found.** The actual PVE 7 cgroup breakage found was *nested* Docker in LXC after the cgroup-v2 transition: `docker run` failed with “cgroup mountpoint does not exist” ([report](https://forum.proxmox.com/threads/proxmox-7-lxc-cgroup-issue-with-docker.92722/)). PVE 9 no longer supports legacy cgroup v1; its upgrade guide calls out only very old system-container guests as unsupported. | **Low for direct host Docker; material for LXC.** Direct Docker shares PVE's modern cgroup-v2 host just as any host service does, so it avoids the LXC cgroup namespace/mount translation. It still means two resource managers use host cgroups; establish and test resource limits rather than assuming an old Docker or guest userspace will work. |
| Docker graph storage on ZFS | **Documented, with a major historical change.** Docker's `zfs` graph driver requires `/var/lib/docker` on ZFS and warns it is not recommended for production without substantial ZFS-on-Linux experience; changing drivers makes existing containers inaccessible ([Docker ZFS driver](https://docs.docker.com/engine/storage/drivers/zfs-driver/)). Older ZFS lacked OverlayFS support. OpenZFS 2.2 added the support needed for overlay whiteouts; PVE 8.1 shipped ZFS 2.2, but a user then reported slow Docker create/build/destroy operations and filed an upstream OpenZFS issue ([report](https://forum.proxmox.com/threads/proxmox-8-1-zfs-2-2-docker-in-privileged-container.137128/), [upstream issue](https://github.com/openzfs/zfs/issues/15581)). Docker 29 also treats legacy `overlay2` as superseded by containerd's OverlayFS snapshotter ([OverlayFS driver](https://docs.docker.com/storage/storagedriver/overlayfs-driver/)). | **A current validation item, not a reason to choose the legacy ZFS driver.** A PVE 9 host has a modern ZFS/kernel stack, so host-side overlay-on-ZFS is substantially less exotic than it was before ZFS 2.2. Still verify `docker info`, an image pull, a Compose create, and an image build on the actual Docker data-root dataset. Put Docker's mutable graph on a purpose-built ZFS dataset and keep durable application data as explicit bind mounts/datasets. Do not choose the Docker `zfs` driver merely because the host uses ZFS. |
| Host blast radius / support boundary | **Documented policy.** The explicit PVE FAQ warning is the primary evidence. The practical consequence is that an application image, Docker update, or Docker network rule becomes a change to the hypervisor, not merely a guest. | **Always applicable.** This is the irreducible trade: no secondary isolation layer and no PVE-managed Docker guest to restore independently. It matters more because this machine owns storage as well as services. |

### Direct-host operating boundary

The absence of a cluster removes HA, migration, Ceph, and quorum interactions. The absence of PVE firewall rules removes the most commonly cited Docker/PVE ruleset collision. It does **not** remove Docker's forwarding policy, host attack surface, package-repository lifecycle, or the fact that PVE officially discourages the arrangement.

A direct-host design is least surprising when treated as a declarative Debian service co-resident with PVE: Ansible owns Docker's apt source/version policy, `daemon.json`, `data-root`, ZFS datasets, Compose files, and any required `DOCKER-USER` / forwarding policy. The required acceptance test is end-to-end: restart Docker, then confirm host access, every VM's relevant network path, published ports, Plex hardware transcode, and ZFS writes. Reconciliation must restore the desired firewall policy after a Docker restart if Docker is allowed to control it.

## Docker inside one PVE LXC

The wrapper gives Docker an independent Debian userspace and a PVE-managed guest object while retaining host-kernel device access. It is nesting, not VM isolation: Docker and LXC still share the PVE kernel and both apply namespace/cgroup/security policy.

### Known seams and historical breakage

| Seam | Evidence | Consequence |
| --- | --- | --- |
| `nesting` and `keyctl` | **Documented.** PVE says `keyctl` is required for Docker in an unprivileged container; without it the syscall is hidden. `nesting` exposes host `procfs` and `sysfs` and is required for systemd service isolation ([Linux Container](https://pve.proxmox.com/wiki/Linux_Container)). | These are explicit non-default LXC features to reconcile and regression-test after LXC/kernel upgrades. They reduce the simplicity/isolation that motivates an LXC wrapper. |
| cgroup-v2 transition | **Report.** After upgrading to PVE 7, an operator changed cgroup configuration but Docker failed with `cgroup mountpoint does not exist`; attempting to revert to legacy cgroups then stopped the LXC from starting ([report](https://forum.proxmox.com/threads/proxmox-7-lxc-cgroup-issue-with-docker.92722/)). PVE 9 removes cgroup-v1 support entirely. | This is a historical major-upgrade failure of nested Docker, not merely a warning. A current Debian 13 / current Docker stack should use cgroup v2, but the nested runtime has an additional compatibility surface that direct host Docker lacks. |
| AppArmor | **Report plus staff security guidance.** An Ubuntu 20.04 LXC could start Docker but failed at `docker run` because it could not load Docker's AppArmor profile. The same thread reports a privileged CT failing while an unprivileged CT worked; Proxmox staff warned that an unrestricted AppArmor profile enables an LXC escape and recommends unprivileged CTs unless there is a strong reason ([report](https://forum.proxmox.com/threads/docker-with-ubuntu-lxc-20-04-template.84005/)). | “Set AppArmor unconfined” is not a neutral fix. It trades a workload compatibility issue for a declared reduction in host protection. This must be exercised with the actual images, especially Plex and stacks that create nested profiles. |
| OverlayFS on ZFS | **Reports, evolved kernel/ZFS capability.** Before newer kernels/ZFS, users fell back to `vfs`, `fuse-overlayfs`, or an ext4 filesystem on a ZFS zvol. A 2023 PVE forum thread records `overlay2` beginning to work with a PVE 6.1 kernel, but also reports a Nextcloud-image failure and a separate post-move failure to start Docker on ZFS ([thread](https://forum.proxmox.com/threads/lxc-zfs-docker-overlay2-driver.122621/)). PVE 8.1/ZFS 2.2 made native overlay support viable but its reporter found slow lifecycle operations, as above. | PVE 9 improves the baseline; it does not erase the nested OverlayFS compatibility test. Avoid carrying an old `vfs`, `fuse-overlayfs`, or forced graph-driver workaround into the rebuild without proving it is still necessary. |
| Runtime policies change independently | **Staff statement.** Fabian's “inherent conflict” explanation is the most direct description of why nesting can regress: LXC and Docker both want to govern namespaces, cgroups, mounts, and security constraints. | This is the residual major-version risk even after a clean PVE 9 build. It should be documented in host configuration rather than accumulated as ad-hoc `lxc.*` exceptions. |

### Privileged versus unprivileged, datasets, and QuickSync

A **privileged** LXC sees host IDs directly, making a `/dev/dri` device bind mount and host-dataset ownership straightforward. The cost is serious: PVE's LXC documentation says the LXC project considers privileged containers unsafe and does not treat new escape exploits as security bugs worthy of a CVE/quick fix. Docker inside that container is an additional privileged control plane.

An **unprivileged** LXC is the safer starting point. PVE maps container root to a high, unprivileged host ID (normally 100000), so a container escape normally lands as an unprivileged host user ([Unprivileged LXC containers](https://pve.proxmox.com/wiki/Unprivileged_LXC_containers)). It works with Docker when `nesting=1,keyctl=1` are set, but it makes this NAS's two important pass-throughs deliberate engineering work:

- A host ZFS dataset bound into the CT is not automatically usable by the Docker workload's expected `PUID:PGID` (currently `950:544`). PVE documents that otherwise files appear as `nobody` and writes receive high mapped IDs. The supported pattern is explicit `lxc.idmap` entries plus matching `/etc/subuid`, `/etc/subgid`, and ownership on the host path. This is feasible and Ansible-friendly, but every application UID/GID and shared dataset is part of the host/CT interface contract.
- `/dev/dri/renderD*` is a character device owned by a host group such as `render`. The CT needs an allowed device node and a group mapping that lets Plex's render group use that node. The same user-namespace mapping issue applies; a one-off mapping for the host render group must not accidentally map CT root to host root. Validate with the final Plex image and a real hardware transcode, not merely `ls /dev/dri`.

### What the LXC wrapper buys—and does not buy

PVE can back up and snapshot the LXC's **storage-backed** rootfs and tracks its configuration, startup order, resource limits, and console as one guest. That makes Docker packages, Compose renderer state, and the Docker graph independently recoverable from the hypervisor. It also contains Docker's iptables/nftables changes inside the LXC network namespace, leaving PVE bridge/firewall state untouched.

Do not overstate that value for this NAS. PVE documents that arbitrary bind mounts are outside its storage subsystem: they cannot be snapshotted or quota-managed as PVE volumes, and **“The contents of bind mount points are not backed up when using vzdump.”** On restore, PVE restores their configuration only. ([PVE container mount points and restore](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#pct_mount_points)). The important capacity/performance datasets must retain their own ZFS snapshot/replication/backup policy either way. The LXC backup is therefore a useful wrapper/config/graph recovery mechanism, not an atomic backup of the Compose application and its host datasets.

## What operators report over time

This is not a survey. It separates persistent reports from the much larger volume of installation tutorials and one-week success claims.

- **Nested LXC has genuine long-running users.** A PVE forum subscriber reported in July 2022 that seven unprivileged Docker LXCs, 25 containers total, had run for two years without problems; their Docker graphs were XFS filesystems on ZFS volumes, not native ZFS-backed overlay ([report](https://forum.proxmox.com/threads/proxmox-7-1-and-docker-lxc-vs-vm.105140/)). That demonstrates a stable workaround, not that the current native ZFS path was stable for two years.
- **Nested LXC failures recur at substrate boundaries.** The cgroup-v2, Ubuntu AppArmor, and ZFS-overlay reports above span 2021–24. This supports Proxmox staff's claim that workarounds can break with kernel, LXC, or Docker changes. It does not show that every LXC Docker host fails on upgrades.
- **Direct PVE host use exists, but high-quality longitudinal evidence is thin.** In the 2024 direct-host PVE thread, an operator who chose LXC despite the advice said it worked well, except PVE guest disk-write and then network-traffic summary metrics became increasingly non-functional across upgrades ([report](https://forum.proxmox.com/threads/running-docker-on-the-proxmox-host-not-in-vm-ct.147580/)). The same thread contains the concrete forwarding-policy warning. There was no comparable multi-year, Ansible-managed direct-host report in the primary material found.
- **Config-managed operators should weight reversibility, not popularity.** Neither option prevents declaring the machine in Ansible. Direct host makes the reconciler own one OS and its policy interactions. LXC makes it own a PVE guest plus a nested OS plus ID/device mapping. The latter is more objects, but Docker package upgrades and firewall changes are separated from PVE; the former has less configuration but a larger hypervisor blast radius.

The community record is therefore not a numerical verdict. It says both are operated successfully, but the failure reports divide along their expected boundaries: host Docker hits global packet filtering and apt ownership; nested Docker hits LXC cgroups, AppArmor, ID maps, and overlay/mount semantics.

## A third path: make this a Debian Docker NAS, not a PVE host

Plain Debian 13 with ZFS and Docker is the natural fit for an Ansible-owned Compose host: Docker uses its supported Debian installation path, ZFS datasets are local, `/dev/dri` is local, and Docker owns the only host firewall integration. The occasional agent-platform VM can be run with KVM/QEMU plus libvirt. Debian's [KVM documentation](https://wiki.debian.org/KVM) describes `libvirt-daemon-system`, `virtinst`, and `virsh` as the normal management layer; libvirt has a stable API that Ansible can drive. Incus is another possible one-host manager for system containers and VMs, but adding it solely for one or two VMs brings an LXC-oriented control plane and should not be mistaken for reducing nesting complexity.

This alternative loses PVE's integrated guest UI/console, guest lifecycle API/UI, PVE storage abstractions, scheduled guest backup integration, and its easy QEMU/LXC provisioning. It also means this repository must own VM networking, image lifecycle, backup integration, and VM definitions more directly. With no cluster, HA, Ceph, or PVE firewall requirement, those are the remaining reasons for PVE to earn its place.

Conversely, Docker directly on a PVE host uses PVE primarily as an occasional-VM manager while knowingly bypassing its recommended application-container boundary. That can still be rational if the PVE VM tooling and familiar recovery workflow are valued enough, but it is not free: the direct-host Docker acceptance and upgrade checks become permanent PVE maintenance work. Plain Debian eliminates that particular conflict rather than mitigating it.

## Framing for this rebuild—without deciding

| Constraint | Direct PVE-host Docker | Docker in one LXC | Plain Debian + libvirt/Incus |
| --- | --- | --- | --- |
| QuickSync and ZFS datasets | Native access; simplest operational path. | Native kernel access remains, but `/dev/dri` and `950:544` dataset access need privileged CT acceptance or unprivileged ID/device mapping. | Native access; same simplicity as direct host. |
| PVE firewall unused; UniFi segments | Removes most PVE-firewall collision risk, but Docker's own forwarding policy still needs exact-network testing. | Docker firewall state stays inside CT; PVE's host rules stay separate. | Only Docker's policy exists; no PVE ruleset collision. |
| One or two VMs, no cluster | PVE still provides useful VM management, but direct Docker shares the hypervisor blast radius. | Preserves PVE's intended host/guest boundary at the cost of a known unsupported nesting seam. | Requires declaring VM operations ourselves; avoids PVE/Docker co-residency. |
| Ansible as source of truth | One OS to reconcile; must own PVE and Docker interactions exactly. | More declarations: PVE CT, nested Debian/Docker, feature flags, mappings, and dataset contracts. | One OS to reconcile plus libvirt/Incus VM definitions. |
| Upgrade risk | Apt/repository and global network policy must be included in every PVE major-upgrade runbook. | PVE upgrade plus nested Docker/LXC compatibility smoke test; historical cgroup/AppArmor/overlay regressions matter. | Debian/Docker release upgrade only; VM manager has its own but narrower lifecycle. |
| Backup semantics | ZFS data snapshots plus an independent config/Compose/Docker-graph recovery plan. | PVE can recover the wrapper/rootfs/graph, but not bind-mounted datasets; ZFS data policy remains mandatory. | ZFS data snapshots plus explicit VM and Docker host backup policy. |

For the stated constraints, the important distinction is not “Docker works”—both can. It is whether the durable contract should be **PVE host + Docker policy**, or **PVE LXC policy + Docker policy + explicit ID/device mappings**. The third path asks whether occasional VM management justifies maintaining PVE at all when the primary workload is an Ansible-managed Debian Docker NAS.
