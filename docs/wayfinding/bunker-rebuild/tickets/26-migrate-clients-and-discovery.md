# Migrate approved clients and scoped discovery

## Question

Import the approved old-house client records, broadcast the required Scanners and The Village WLANs, and move devices into their selected trust domains in controlled cohorts. Finish by enabling only the discovery paths the target model requires.

## Work

- Add approved `unifi_client` resources for names and reservations. Import existing live objects before apply and require a zero-change or intentionally additive plan; never recreate randomized or stale client records.
- Store WLAN credentials in 1Password and R2 state only. Choose the narrowest security and radio compatibility supported by each approved client cohort.
- Migrate infrastructure, administrator, household, discovery, and appliance cohorts separately. After each cohort, confirm DHCP, DNS, Internet, intended zone access, and intended denial before moving the next.
- Declare the custom mDNS proxy through `unifi_setting.mdns` so it reflects only selected services between YoRHa and Scanners and between Lunar Tear and Scanners. Keep Bunker and The Village outside the reflection scope.
- Test real discovery behavior for retained Apple, Google, receiver, console, printer, and future Home Assistant paths represented in the approved inventory. Add named unicast policy exceptions only when a captured failure identifies a required protocol and endpoint.
- Restore Transporter WireGuard and Identity VPN material only from verified preserved state. Test its intended administrator reach without broadening ordinary LAN zones.
- Leave fixed-location AP pinning and RF values to [WiFi coverage survey and RF tuning](21-wifi-coverage-and-tuning.md), after every AP reaches its final location.

The print sheet listed it. `_universal._sub._ipp._tcp.local` was added as a custom service because iOS browses `_ipp._tcp,_universal` rather than the bare type.
- Correction to everything below: on this firmware the gateway runs two mDNS mechanisms at once, and the documentary account of avahi alone is incomplete. A live capture on the Scanners segment shows the gateway at `10.10.40.1` doing a per-minute cycle, enumerating `_services._dns-sd._udp.local` and then browsing only the service types that enumeration returned, which matches the `ubntmdnsd` cron job the firmware research describes. Separately it relays client queries verbatim: a macOS printer browse arrives as the exact set `_ipps, _uscans, _uscan, _ipp, _ippusb, _printer`, including types nothing declares. So `_airplay` and `_hue` repeat on the gateway's own cadence while the printer types appear only when a client asks.
- The Canon does not answer `_services._dns-sd._udp` enumeration, tested three ways, though it answers every direct type query including the `_universal` subtype. So the gateway never learns on its own that `_ipp._tcp` exists on Scanners, and the printer is absent from the warm browse set the HomePod and Hue bridge occupy. Discovery still works because iOS's own browse is relayed live and the printer answers it. A beacon that answers enumeration with the printer's types made the gateway add them to its browse set within one cycle and drop them one cycle after the beacon stopped, which is as direct a demonstration of the mechanism as this box will give without SSH. The practical consequence: printing works while a client is actively browsing, but the printer never benefits from the gateway's cache the way an AirPlay target does. If discovery is ever slow or intermittent, this is why, and a permanent type beacon on Scanners is the fix.
- What the gateway is actually doing with the service lists. The mDNS Proxy configures `avahi-daemon` in reflector mode through a generated `/run/avahi-daemon.conf`, where `enabled_for_network_ids` becomes `allow-interfaces` and the service lists become avahi's undocumented `reflect-filters`. Reading avahi's `avahi-core/server.c` settles what those filters gate: `reflect_query()` consults no filter at all and relays every question to every member interface, while `handle_response_packet()` substring-matches each answer against the filter list before reflecting or caching it. So the lists gate responses, not queries, which is exactly why `_ippusb`, `_printer`, and `_pdl-datastream` queries appeared on Scanners despite none being declared. A records bypass the filter entirely, so a Scanners host's `.local` address crosses to YoRHa whether or not a declared service covers it, which is worth knowing next to the segmentation invariant.
- `_universal._sub._ipp._tcp.local` is dead weight, not merely redundant. PTR filtering matches the record's target, and a subtype PTR targets the same instance name, `Canon MF650C Series._ipp._tcp.local`, which the plain `_ipp._tcp.local` entry already permits. The `_sub` string itself matches no record avahi will ever see. Remove it once the cold-cache test below passes, not before; the chain rests on an avahi mapping nobody has read off this box.
- The address format is validated by the controller against `^_[a-zA-Z0-9._-]+\._(tcp|udp)(\.local)?$`, so the trailing `.local` is optional and a trailing dot is rejected. The provider applies no validation of its own, so a bad value fails at apply rather than at plan.
- The controller has 24 predefined service codes, including `printers`, `scanners`, and `philips_hue`, which could replace five of the six custom entries. What each expands to is not published anywhere. Settle it by adding one code at a time and diffing `reflect-filters` in `/run/avahi-daemon.conf` over SSH; do not swap blind.
- The filter runs before the cache is updated, so a rejected record never enters the cache and adding a service never retroactively populates it. The cache fills on the next announcement, which is the real substance behind community reports that custom mode "needs a gateway restart". It also gives the printer's fix a coherent shape: the `_ipp` and `_uscan` entries were already in place, enabling AirPrint made the printer announce, and avahi accepted and cached those announcements because the filter permitted them. Both halves were necessary.
- Service scope is one flat list across every scoped interface. There is no way to reflect AirPrint to YoRHa but not to Lunar Tear. Matching is unanchored `strstr`, so short entries over-match: `_ipp` alone would also admit `_ipps` and `_ippusb`.
- `enabled_for` and `enabled_for_network_ids` are absent from the controller's own field spec and exist in the provider fork only because a live controller drops the scope when a write omits them. Any other writer of this setting will silently widen the reflection to every network.
- To settle any of this without guesswork, `avahi-daemon` logs its filter decisions at debug level as `Match Ptr`, `Reject Ptr`, and `Reject Key` lines. Tailing that on the gateway while browsing from YoRHa shows, per record, exactly what the reflector admits, and would prove the subtype entry never matches. `cat /run/avahi-daemon.conf` over SSH answers the rest in one command: whether `reflect-filters` exists at all, whether the `.local` suffixes survived the write, and what `apple_airPlay` and `homeKit` expand to.
- Caching is real and cuts against the successful run below. `reflect_query()` answers a browse from the other interface's cache to work around known-answer suppression, so a query from YoRHa can be served entirely from the gateway's Scanners-side cache with the printer silent. A reflector subscribes no local browser, so reflected entries expire rather than refresh; with the conventional 4500-second PTR TTL the cold test needs roughly 75 minutes of quiet.
- Worth watching, from the same research: UniFi OS 5.1.26 added one-shot mDNS queries from ephemeral ports, and the predefined `Allow mDNS` zone policy matches destination port 5353 only, so the unicast replies fall to the default block. Several UDM Pro owners report six-figure daily block counts and broken cross-VLAN discovery from exactly this. If discovery becomes flaky, look for blocked UDP with source port 5353 toward the Gateway zone before touching anything here.
- Two things about that run are not yet proven, and both matter before calling this settled. The gateway also relayed queries for `_ippusb._tcp`, `_printer._tcp`, and `_pdl-datastream._tcp`, none of which are declared, so `custom_services` evidently does not gate which queries cross; it most likely gates which responses are relayed, which would make the `_universal` entry redundant rather than load-bearing. And the successful print sheet followed a print through the Canon app roughly forty seconds earlier, which may have warmed the proxy's cache. The clean test is a cold print sheet after the cache expires, with no Canon app beforehand. Do not remove the subtype entry until that test passes twice.
- `printer.thurstons.house` resolves to `10.10.40.187` from both the Bunker and Scanners resolvers. That required pinning the lease, so the client carries `fixed_ip` inside the DHCP pool rather than a low static like `home-assistant`'s `10.10.40.42`; the printer already held the address and renumbering it during an outage was not worth the consistency.
- The cold test failed, and so did adding the predefined `printers` and `scanners` groups, which settles the enumeration gap as the cause rather than the cache. The fix is a permanent type beacon at `bootstrap/targets/pod042/containers/stacks/mdns-beacon/`: a stdlib-only container holding its own macvlan identity, `10.10.40.250`, named `pod042 mDNS Beacon` in the controller. It answers `_services._dns-sd._udp.local` with the five printer types and publishes no instances, so it cannot invent a printer. From its first minute the gateway's own cycle browsed all five on Scanners. The container is the only thing on VLAN 40 besides Home Assistant; macvlan isolates it from pod042 itself and it publishes no ports, so it adds a named client rather than a host interface.
